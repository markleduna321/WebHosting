# Invoices: Tax, PDF Download & Email

### Phase 1: Proper invoices + PDF download

- **Timestamp:** 2026-10-03
- **Mode:** Agent
- **Persona(s) Active:** ⚙️ Backend (lead), 🖥️ Frontend + 🎨 Designer, 🧪 QA
- **Decisions (asked the user before planning):**
  - Tax is shown inside the price; the customer's total never changes.
  - The seller is **Non-VAT registered**, so invoices show a "Non-VAT Registered Seller" note and no VAT line. The VAT breakdown is built in behind `INVOICE_VAT_REGISTERED`.
  - PayMongo's fees and taxes are saved for the seller's records only and are never shown to the customer.

- **Files Modified/Created:**
  - `composer.json` / `composer.lock` — Added `barryvdh/laravel-dompdf` ^3.1.
  - `config/invoice.php` — Created. Seller details (optional TIN), VAT switch and rate, invoice number prefix, logo path.
  - `.env.example` — Documents `INVOICE_SELLER_TIN`, `INVOICE_VAT_REGISTERED`, `INVOICE_NUMBER_PREFIX`.
  - `database/migrations/2026_10_03_020000_add_invoice_fields_to_payments_table.php` — Created.
    - Adds `invoice_number` (unique), `invoice_issued_at`, `line_items` (json), `paymongo_fee`, `paymongo_foreign_fee`, `paymongo_tax_amount`, `paymongo_net_amount` (centavos) and `paymongo_taxes` (json).
    - Gives existing paid payments invoice numbers in the order they were paid (an amendment, see Issues).
    - `down()` drops all of it.
  - `app/Models/Payment.php` — New columns are fillable; `line_items` and `paymongo_taxes` are arrays, `invoice_issued_at` is a date.
  - `app/Services/InvoiceService.php` — Created.
    - `assignNumber()` gives sequential numbers like `CAL-2026-000001`. It runs inside the transaction that marks the payment paid and locks the latest number so two simultaneous payments can't collide; the unique index is the backstop.
    - `build()` puts together the line items, totals, tax, seller, buyer and payment method.
    - `pdf()` / `filename()` produce the PDF and a safe filename.
    - VAT math is done in centavos: `vatable = round(total/1.12)`, `vat = total − vatable`, so the two always add up exactly.
    - If a payment's saved line items are missing or don't add up to the amount charged, the invoice shows one summary line instead.
  - `app/Services/CheckoutService.php`
    - `priceFor()` now also returns the line items: the plan, plus each add-on with its quantity (number of months) and unit price.
    - `start()` saves those line items on the payment.
    - `markPaid()` accepts PayMongo's payment attributes, stores the sanitised fee and tax figures, and assigns the invoice number inside the same transaction.
  - `app/Services/PaymentMethodRegistry.php` — Added `label($id)`.
  - `app/Http/Controllers/Api/PayMongoWebhookController.php` — Passes PayMongo's payment attributes to `markPaid` (from `data.attributes` for `payment.paid`, and `payments[0].attributes` for checkout sessions).
  - `app/Http/Controllers/InvoiceDownloadController.php` + `routes/web.php` — `GET /account-billing/invoices/{payment:uuid}/download` (`invoices.download`, `auth`, `throttle:30,1`). Checks `PaymentPolicy::view` and returns 404 unless the payment is paid and numbered.
  - `resources/views/invoices/pdf.blade.php` — Created. A4 print layout with inline styles and DejaVu Sans; shows VAT lines or the Non-VAT note.
  - `public/images/invoice-logo.png` — Created. A 160×131 px, 18 KB copy of `logo 3.png`, made once.
  - `app/Http/Resources/PaymentResource.php` — Adds `invoice_number` and an `invoice` block (items, subtotal, tax, total, payment method, issue date, `download_url`) for paid payments. The `paymongo_*` columns are never included; checked by test.
  - `app/Http/Controllers/AccountBillingController.php` — Attaches the logged-in user to each payment so building invoices doesn't run one extra query per row.
  - `resources/js/pages/account-billing/_sections/InvoiceSection.jsx` — Invoice number, a row per line item (qty, unit price, amount), subtotal, VAT lines or Non-VAT note, total, "Paid via", a **Download PDF** button, and a layout that stacks on phones (the item table scrolls sideways if needed).
  - `resources/js/pages/account-billing/_sections/SubscriptionInvoiceHistorySection.jsx` — Shows the invoice number and a download icon link (44px) on paid rows. Clicking it doesn't also open the row.

- **Issues Encountered:**
  1. `composer require` reported exit code 1.
  2. **Plan gap:** existing paid payments had no invoice number, so they couldn't be downloaded.
  3. **PDF render failed with a fatal out-of-memory error.** Every project logo is 4,688–6,250 px (`logo 3.png` is 5017×4110, about 80 MB once decoded), which is over PHP's 128 MB limit. Shrinking it while the app runs also failed, because GD had to decode the full image first.
  4. The first working PDF was 898 KB because the whole DejaVu font was embedded.
  5. One no-op entry in a batch edit was reported as failed.
- **Resolution:**
  1. Confirmed the package is installed (`vendor/` present, `package:discover` lists it). The exit code came from how PowerShell handles output piped through `Select-Object`.
  2. The migration numbers existing paid payments in order, year by year. This is a small amendment within the planned migration.
  3. Made a small 160px copy of the logo once from the command line (raising memory for that one command only). `config/invoice.php` points at it, and `logoDataUri()` won't load any file larger than 512 KB. No memory limit is raised at runtime.
  4. Turned on `isFontSubsettingEnabled`: the PDF is now **43 KB**.
  5. Checked the file: every intended change was applied.

- **Verification (in-memory models; nothing saved to the database; no external calls):**
  - Non-VAT mode returns the note and no VAT lines.
  - VAT mode for ₱1,647.00: vatable ₱1,470.54 + VAT ₱176.46, which adds back to the total exactly.
  - A 2-item snapshot shows both lines. A snapshot that doesn't add up falls back to the "Student plan" summary line.
  - The PDF output starts with `%PDF-`, is 43,082 bytes, and is named `Invoice-CAL-2026-000001.pdf`.
  - `PaymentResource` output contains no `paymongo` fields.
  - `route:list` shows `invoices.download`. All PHP lints clean and the editor reports no errors.
  - A sample PDF is at `storage/app/sample-invoice.pdf` for a visual check. The temporary smoke script has been deleted.

- **QA Checklist Result:**
  - ✅ JS purity: plain JavaScript.
  - ⚠️ `web.php` rule deviation: the download route streams a PDF file. It can't be an Inertia render, and `api.php` is JSON-only. It sits in `web.php` because it needs the logged-in session. The reason is noted in the route file and in the approved plan.
  - ➖ Form Request: no new POST/PUT endpoints.
  - ✅ Policy: `PaymentPolicy::view` (owner only), plus a 404 when the payment isn't paid.
  - ✅ Resource: `PaymentResource` is extended; PayMongo's fee columns are not included.
  - ✅ Migration is reversible.
  - ✅ Service class: `InvoiceService` holds the logic; the controller is thin.
  - ➖ RTK Query: no new endpoints. Invoices come with the billing page (Inertia props), as before.
  - ⚠️ Links: the download links are plain `<a download>`, deliberately. An Inertia `<Link>` would request the PDF as page data instead of downloading the file.
  - ✅ No new shared UI component.
  - ✅ Loading state: the browser handles the download natively; nothing to load inside the page.
  - ✅ Empty state: the existing "No invoices yet" message is kept.
  - ✅ Keyboard and a11y at code level, needs browser check: download links have `aria-label`, focus rings and 44px targets.
  - ✅ Responsive at code level, needs browser check: the invoice stacks at `sm`, the item table scrolls sideways on narrow screens.
  - ✅ Security:

    - The filename is cleaned with a regex.

    - PayMongo's fee data never reaches the browser.

  - ✅ Guarded commands: none. Ran `composer require`, `php -l`, `route:list`, the in-memory smoke test, and the one-off logo resize.

- **User actions required:**
  1. **Start MySQL.** The latest log entry is a "connection refused" error from MySQL.
  2. Run `php artisan migrate`. This adds the invoice columns and numbers existing paid payments. **Required** before the next payment: `markPaid` now writes these columns.
  3. Optional: put your BIR TIN in `INVOICE_SELLER_TIN`. Set `INVOICE_VAT_REGISTERED=true` only once VAT registration is approved.
  4. Open `storage/app/sample-invoice.pdf` to check the layout, then delete it.
  5. Ask your accountant whether this PDF can serve as your official BIR receipt or invoice. Non-VAT sellers usually still owe 3% percentage tax, which is your obligation and isn't shown to the customer.

### Phase 2: Invoice email via Resend (sent once, after payment and plan activation)

- **Timestamp:** 2026-10-03
- **Mode:** Agent
- **Persona(s) Active:** ⚙️ Backend (lead), 🎨 Designer, 🧪 QA
- **Files Modified/Created:**
  - `database/migrations/2026_10_03_030000_add_invoice_emailed_at_to_payments_table.php` — Created. Adds `invoice_emailed_at` (nullable); `down()` drops it.
  - `app/Models/Payment.php` — `invoice_emailed_at` is fillable and stored as a date.
  - `app/Services/InvoiceMailer.php` — Created.
    - `payload()` builds the HTML email, subject, sender address, and the PDF attached as base64 with its safe filename.
    - `transport()` sends through Resend using `config('services.resend.key')`. It's a separate protected method so tests can replace it.
  - `app/Jobs/SendInvoiceEmailJob.php` — Created. Queued job that retries 3 times, waiting 1, 5, then 15 minutes.
    - Skips payments that aren't paid or numbered.
    - Marks the email as sent *before* sending, with a single update that only succeeds if it wasn't already marked. Duplicate jobs therefore can't both send.
    - If sending fails, it clears the mark so the retry can send, logs the payment id, invoice number, attempt and error (never the email body or PDF), and rethrows so the queue retries.
  - `app/Services/CheckoutService.php`
    - `markPaid()` queues the email job *after* the transaction commits.
    - If a payment is already paid but no email went out, a repeated PayMongo webhook queues the email again.
    - A failure to queue is logged and never fails the webhook.
  - `resources/views/emails/invoice-paid.blade.php` — Created. Email-client-safe HTML (tables and inline styles, hidden preview text):
    - Greeting, "your {Plan} plan is active", invoice number, paid date and payment method.
    - Line items, then VAT lines or the Non-VAT note, then total paid.
    - "Go to your dashboard" button and an Account & Billing link.
    - Seller footer.
  - `config/services.php` — `resend.from` = `RESEND_FROM_ADDRESS`, falling back to `MAIL_FROM_ADDRESS`.
  - `.env.example` — Documents `RESEND_FROM_ADDRESS`.

- **Issues Encountered:** None. Every edit applied and was checked first time.

- **Verification (in-memory models; Resend transport faked; no email sent; nothing saved to the database):**
  - Exactly one send, from `CALEHO Host <billing@example.com>`, to the customer, with subject `Payment received — Invoice CAL-2026-000001`.
  - Attachment `Invoice-CAL-2026-000001.pdf` decodes back to a valid `%PDF-` file (56 KB as base64).
  - A name containing HTML (`Maria <b>Clara</b>`) appears escaped in the email.
  - The email contains the plan, the total and the Non-VAT note.
  - A rendered sample is saved at `storage/app/sample-invoice-email.html`. The temporary smoke script has been deleted.
  - All PHP lints clean and the editor reports no errors.
  - **Not tested here:** the duplicate-send protection needs a live database (MySQL was down) and wasn't run. I checked the code by reading it.

- **QA Checklist Result:**
  - ✅ JS purity: no JS changed this phase.
  - ✅ `web.php` / `api.php`: unchanged.
  - ➖ Form Request / Policy / Resource: no new endpoints.
  - ✅ Migration is reversible.
  - ✅ Service class plus job: the logic is in `InvoiceMailer` and `SendInvoiceEmailJob`; `CheckoutService` only queues the job.
  - ➖ RTK Query and UI states: not applicable (server-side email).
  - ✅ Email design: table layout for email clients, readable at 560px or narrower, real link for the button, colour isn't the only signal.
  - ✅ Security:
    - The Resend key stays on the server; the email body and PDF are never logged.
    - All values in the template are escaped by Blade; the attachment filename is cleaned.
    - Emails can't send twice (the mark is set atomically before sending).
    - Email trouble can't block plan activation or make PayMongo keep re-sending the webhook.
  - ✅ Guarded commands: none. Only `php -l` and the in-memory smoke test ran.

- **User actions required:**
  1. Start MySQL, then run `php artisan migrate`. This runs both invoice migrations, if you haven't already.
  2. Set `RESEND_FROM_ADDRESS` to an address on a domain you've **verified in Resend**. Resend rejects unverified senders; in test mode only `onboarding@resend.dev` works, and only to your own address.
  3. Keep a queue worker running: `php artisan queue:work`. Your queue uses the `database` connection, so emails wait in the queue until a worker runs.
  4. `APP_URL` is `http://localhost`, so email links will point to localhost until it's set to your public domain in production.
  5. Open `storage/app/sample-invoice-email.html` in a browser to check the design, then delete it along with `sample-invoice.pdf`.
  6. End-to-end test with PayMongo test keys: pay → the plan activates → within seconds of the worker running, the email arrives with the PDF attached.

- **Next Steps:** None scoped. Possible follow-ups:
  - An admin button to resend an invoice.
  - Mark existing paid payments as already emailed, so a replayed old webhook can't email an old invoice.
  - An admin report of PayMongo fees and net earnings from the stored `paymongo_*` columns.
